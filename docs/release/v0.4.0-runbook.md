# PrismPM v0.4.0 release runbook

This runbook takes PrismPM from "LexLean v0.4.0 is tagged" to "prism-code binds
the PrismPM v0.4.0 SDK and `just vv` passes". It serves issue
[#194](https://github.com/UOR-Foundation/PrismPM/issues/194), which closes the
"PrismPM v0.4.0" milestone tracked by
[#211](https://github.com/UOR-Foundation/PrismPM/issues/211).

It is written against `main` at `30c3acf3` (2026-10-22). Citations use
`path:lines` at that commit unless they name another ref. A line that names a
workflow or script that later changes must be rechecked before it is run.

## What "released" means

- **Release policy.** "Development imports upstream commits between releases; a
  release pins only upstream releases." PrismPM v0.4.0 is held until LexLean
  v0.4.0 is released and imported ([#211](https://github.com/UOR-Foundation/PrismPM/issues/211)
  body, policy paragraph; restated by afflom on #194,
  [comment 6321301002](https://github.com/UOR-Foundation/PrismPM/issues/194#issuecomment-6321301002)).
- **#194 acceptance.** "A template instance on language 1.2 passes `prismpm
  template check` against the release" (#194 body, "Accepted when").
- **Milestone done.** "PrismPM v0.4.0 is released pinning only LexLean v0.4.0, a
  prism-code instance binds it in `prismpm.lock`, `just vv` passes in its
  devcontainer, and its Pages site and CLI are generated by the SDK" (#211 body,
  "Done when").
- **prism-code release binding.** `prismpm.lock` names the PrismPM v0.4.0
  release SDK, `template.lock` names a template release, both checks pass, and
  `just vv` passes in the devcontainer
  ([prism-code#4](https://github.com/UOR-Foundation/prism-code/issues/4) body,
  release-binding acceptance).

`prismpm template check` alone does not prove the objective: prism-code's
`just vv` never runs `prismpm check`, so it goes green with an SDK that cannot
check its language-1.2 model
([prism-code PR #35](https://github.com/UOR-Foundation/prism-code/pull/35)
body). Step 10 therefore adds explicit `check`, `build`, `verify`, Pages and
CLI evidence.

## Who runs what

  created by Alex Flom (`gh api repos/UOR-Foundation/PrismPM/git/tags/a9a36e46…`).
  No file names who tags v0.4.0.
- **[member]** marks a step any organization member with write access can do:
  branches, pull requests and `workflow_dispatch` runs.

## Steps

### 1. Land the v0.4 stack on `main` [afflom]

The SDK must carry language 1.2, text/3 with its CLI, the application records
and the Pages command before it is worth releasing (#211 items). Today's open
PRs and their order are under "Known blockers". Each merges only with green CI,
which on #224 and every PR stacked on it needs step 3's goldens first.

### 2. Import the LexLean v0.4.0 release and relock [member, merge afflom]

On a branch from `main`, replace every LexLean 0.3.0 pin with the v0.4.0 tag
commit and crate. Each of these hard-codes the current pin or version:

- `model/dependencies.toml:36-50`: `version`, `revision`, `vendor/lexlean/MANIFEST.sha256` and `vendor/lexlean/lexlean-0.3.0.crate` digests.
- `.github/workflows/m0-lexlean-reconcile.yml:20`: `LEXLEAN_SOURCE_SHA`. The workflow has no dispatch inputs (`:3-6`), so the pin is edited in the file.
- `scripts/reconcile-lexlean.mjs:104,157`: `assert.equal(version,'0.3.0',…)`. If LexLean v0.4.0 ships crate version `0.4.0`, these assertions refuse it until changed.
- `xtask/src/audit.rs:435` and the test-driver `Cargo.toml` files that pin `lexlean = "=0.3.0"`.
- SPEC.md:823-837, the one imported Lean-source exception, names the LexLean package and revision.

Then dispatch `Prepare M0 LexLean reconciliation patch`
(`.github/workflows/m0-lexlean-reconcile.yml`) on that branch:

```bash
gh workflow run m0-lexlean-reconcile.yml --repo UOR-Foundation/PrismPM --ref <import-branch>
```

It vendors the pinned LexLean, relocks every `lexlean.toml` that has a
`lexlean.lock` (`:78-98`), runs `just codegen`, `just fixtures-write`,
`just golden-write` and `just stdlib-package-write` in the devcontainer
(`:113-116`), repackages `prism-stdlib-0.2.0.crate` and `stdlib/release.json`
(`:117-143`), re-checks (`:144-147`), and uploads
`m0-lexlean-reconciliation-proposal` with `reconciliation.patch` (`:150-175`).
Apply the patch to the branch and commit it. The artifact is marked unaccepted
(`UNACCEPTED.txt`): review is the acceptance.

### 5. Prove the objective on a development candidate [member]

Before tagging, build a candidate from the release commit on `main` and run the
whole objective against it. A candidate is not a release (RELEASE-STATUS.md:20),
but it is the same recipe (`.github/workflows/sdk-candidate.yml:72-147`).

```bash
gh workflow run sdk-candidate.yml --repo UOR-Foundation/PrismPM --ref main -f development_only=true
```

Only `main` can publish: `policy`, `build` and `publish` require
`github.ref == 'refs/heads/main'`, and `scripts/sdk-candidate.mjs:24-31,90`
asserts the `sdk-candidate` environment's single `main` branch policy. The run
pushes `ghcr.io/uor-foundation/prismpm-sdk-candidate:sha-<commit>` (index) and
`…-amd64`/`…-arm64` (children) (`:198-206`), and uploads
`sdk-candidate-reference`.

Bind a prism-code branch to it with step 9's procedure and run step 10's
evidence. A failure here costs a candidate, not a release.

### 8. Publish the SDK index with both child manifests [`release.yml`, afflom]

`release.yml` jobs, in order (`.github/workflows/release.yml`):

1. `gate` (`:32-64`): policy, clean tree, version check, two source `just vv` runs.
2. `images` (`:74-257`): six images under `ghcr.io/uor-foundation`, including
   `prismpm-sdk`, each built for `linux/amd64,linux/arm64` and pushed by digest
   (`:147-149`). Both index children are read back (`:156-169`), an SPDX SBOM is
   made per child (`:174-191`), build provenance is attested on the index
   (`:192-197`), and the index is cosign-signed and verified (`:254-257`).
3. `reproducibility` (`:304`), `installed-sdk` (`:494`), `native` (`:563`).
4. `oci-native` (`:645`): checksums and an unaccepted prerelease asset
   publication (`:769-776`, `scripts/release-phases.mjs:308-346`).
5. `crates` (`:783`): runs only when `publish-crates` is true, in environment
   `crates.io` (`:788`).
6. `release` (`:899`): needs all seven jobs including `crates`
   (`scripts/release-phases.mjs:56-61` requires each to succeed). It creates the
   `prismpm-sdk:0.4.0` discovery tag (`:945-961`) and the GitHub release
   `v0.4.0` with `RELEASE_NOTES.md` and `release/*` (`:971-979`).

Record the `prismpm-sdk` **index** digest and both child digests from the
`images` job. Consumers bind the index digest, never the tag (SPEC.md:1506-1531,
RELEASE_NOTES.md:21-25).

As written, the `release` job cannot run without crates.io publication. See
decision 1.

## Decisions the release needs

1. **crates.io.** The `release` job depends on `crates` succeeding
   (`release.yml:899`, `scripts/release-phases.mjs:56-61`). `crates` needs the
   `crates.io` environment, which does not exist (repository environments API
   lists only `sdk-candidate`), and waits for `lexlean 0.3.0` on crates.io
   (`release.yml:878`). The owner deferred first-party crates.io publication
   until Foundry is published (RELEASE-STATUS.md:24). Either publish the crates,
   or change `release.yml` and `release-phases.mjs` so v0.4.0's OCI release does
   not depend on Cargo publication. Since #214, `crates` packages, compares,
   dry-runs and metadata-checks every crate on every release, and uploads only
   with a `CARGO_REGISTRY_TOKEN` secret or trusted publishing, so without either
   it succeeds and `release` is not held for an upload; the owner's first upload
   is one command, in [crates-io-publication.md](crates-io-publication.md).
2. **Who tags `v0.4.0`.** No file says. The precedent is afflom (`v0.2.0`).
3. **SDK lock schemas.** The lock schemas fix `sdk_version` to `"0.3.0"`.
   CHANGELOG.md's compatibility policy says an incompatible schema change needs
   a new schema identifier. Relaxing the constant or adding new schema ids is a
   maintainer call.
4. **Template release identifier.** The contract defines commits A and B but no
   tag. Decide whether a template release also gets a tag.
5. **Release scope.** #211 lists #207's workbench. With the V3 collision open,
   decide whether v0.4.0 waits for it or ships text/3 with the CLI only.
